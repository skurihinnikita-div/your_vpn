## v1.4 (2026-10-06) — Android universal: фикс обрыва в простое (батарея/wakelock)

**Что исправлено:** обрыв через ~100 c после выключения экрана (Doze убивал сокет VPN). Теперь:
- приложение **повторно просит** исключение из оптимизации батареи при каждом запуске и возврате, пока её не выдадут (как в оригинале qWDTT);
- WakeLock держится **непрерывно** во время подключения (без «окон» таймаута);
- сервис возвращает **START_STICKY** (Android сам поднимает его без повторной доставки START).

**Что проверить:**
1. При первом запуске **разрешить «Без ограничений»** (и на Xiaomi/Huawei — автозапуск).
2. Включить VPN, **выключить экран на 10–20 минут**, потом включить — интернет должен быть жив, без обрыва.
3. Прислать лог (с таймстампами и `Screen off/on`) — убедиться, что после `Screen off` нет `software caused connection abort`/пересозданий.
4. Обычные проверки (смена Wi‑Fi↔мобильный, фон, раздельное туннелирование).

## v1.3-diag (2026-10-06) — Android universal: ночной тест простоя (таймстампы + экран + сеть)

**Цель:** поймать случай «телефон лежал заблокированный → пропал интернет во всём телефоне (даже вне VPN) → помогает только перезагрузка».

**Что сделать:**
1. Включить VPN (как обычно, с раздельным туннелированием), убедиться, что интернет есть.
2. **Оставить телефон заблокированным на ночь** (зарядка не обязательна) — ничего не трогать.
3. Утром: проверить интернет **в браузере** и в приложении **вне** раздельного туннеля; проверить, приходят ли уведомления.
4. Сразу снять логи (не перезагружая телефон) и прислать.
5. Дополнительно, если получится: пару раз разблокировать/заблокировать экран днём и снять короткий лог.

**Что смотреть в логе:** строки теперь с **временем** (`HH:mm:ss`) и событиями `Screen off/on`, `Upstream: …`, `VPN interface established/closed`, `Service start: action=…`. По ним видно: один это обрыв или **плотный цикл** пересозданий VPN/перепривязок сети в простое.

**Важно:** другие приложения (вне VPN) тоже без интернета в момент обрыва — это ключевой признак системного сбоя, а не нашего туннеля.

## v1.3 (2026-10-06) — Android universal + Windows portable

**Что проверить:**
1. **Базовое подключение:** VLESS, Amnezia (AWG), WDTT по очереди — открывается ли интернет реально (сайты/видео), а не только «Подключено».
2. **Смена сетей (главное):** Wi‑Fi ↔ мобильный интернет туда‑обратно несколько раз — связь восстанавливается сама за несколько секунд или приходится вручную выкл/вкл VPN?
3. **Потеря/возврат сети:** авиарежим 10–20 c; уйти без сети и вернуться — VPN сам поднимается?
4. **Долгий фон:** оставить VPN на 15–30 минут с выключенным экраном — интернет жив? Сравнить с **отключённой оптимизацией батареи** (приложение само предложит при первом запуске).
5. **Раздельное туннелирование вкл/выкл:** выбранные приложения через VPN, остальные напрямую; не пропадает ли интернет при включённом.
6. **Переключение серверов:** походить по локациям/протоколам, несколько перезапусков подряд.
7. **Случай «залипает после отключения»:** если VPN не включается (помогает только перезагрузка) — **сразу снять логи, НЕ перезагружая телефон**, и описать, что делал до этого.

**Как снять логи:** раздел «Логи» → экспорт/поделиться. Приложить файл + коротко: протокол, что делал (смена сети/авиарежим/фон), что не сработало, восстановилось ли само, помогла ли перезагрузка.

**Важно:** часть обрывов на мобильной сети может быть из‑за оператора (режет UDP) — сравнение «тот же сервер на Wi‑Fi vs мобильном» очень помогает.

### 2026-10-07 — ЗАДАЧА НА БУДУЩЕЕ: ложное предупреждение «Запущен другой VPN» (ZeroTier), НЕ реализовано

1. **(рекомендуемый)** Проверять **таблицу маршрутов**, а не только процессы: предупреждать, только если у другого VPN есть **default route 0.0.0.0/0** (или активный TUN/TAP с шлюзом). Чтение маршрутов не требует прав админа (`Get-NetRoute`/`route print`). ZeroTier/Tailscale без default-route → без предупреждения.
2. Убрать ZeroTier (и, возможно, Tailscale) из `KNOWN`.
3. Оставить, но для subnet-only клиентов показывать мягкую подсказку вместо «Завершить его?».
4. Добавить «Больше не предупреждать про это приложение».

### 2026-10-03 — WDTT (VK-TURN): кэш WG-конфига, широкий таймаут, TCP-TURN по умолчанию

### 2026-10-02 — Фикс: не-ASCII пути ломали запуск ядра на Windows (JNA ↔ Go)

**Симптом:** при подключении на Windows (в т.ч. к WDTT) — `sing-box start failed: start logger: open C:\Users\nïSnïS…\AppData\Roaming\YPtun\singbox.log: The system cannot find the path specified.` Кириллическое имя пользователя `Никита` превращалось в мусор.

**Причина:** JNA по умолчанию кодирует Java-`String` в системную ANSI-кодировку (`native.encoding=Cp1251` на русской Windows), а НЕ в `file.encoding`/UTF-8. Go-ядро (`C.GoString`) ждёт UTF-8, поэтому путь с кириллицей искажался и sing-box не мог открыть лог. Затрагивает любую не-ASCII строку через мост JNA→Go (пути лога/кэша, workDir MasterDNS, путь cronet, JSON-конфиги с кириллицей).

**Диагностика:** harness на Java+JNA (`T.java`, вызов `YpSbStart` с путём `C:\Users\Никита\…\singbox-enc-test.log`):

- по умолчанию (`jna.encoding=null`) → `ERROR=start logger: open …: The system cannot find the path specified`, файл не создан;
- с `-Djna.encoding=UTF-8` → `START OK`, файл создан.

**Исправление:**

- `YPtun/desktopApp/build.gradle.kts` — в `compose.desktop.application.jvmArgs` добавлен `-Djna.encoding=UTF-8` (попадает в `YPtun.cfg` упакованного приложения, проверено).
- `YPtun/desktopApp/src/main/kotlin/main.kt` — первой строкой `fun main` добавлен `System.setProperty("jna.encoding", "UTF-8")` (страховка для запуска из IDE/dev).

**Пересобрано и обновлено в `deliverables/`:** `YPtun-3.6.1-x64-portable.exe`, `YPtun-3.6.1-x64-installer.exe`. Android не затрагивается (gomobile передаёт UTF-8 корректно).

**Факты по архитектуре (без правок кода):**
